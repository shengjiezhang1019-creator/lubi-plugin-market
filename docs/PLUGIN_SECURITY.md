# 插件市场维护指南

2026-10-27：市场工作流和公钥已发布，[初始化工作流](https://github.com/shengjiezhang1019-creator/lubi-plugin-market/actions/runs/40452110063) 已成功生成第 1 版签名空名单，未封禁真实插件。客户端发布与重启另行安排。

## 1. 维护入口与流程

市场仓库：[lubi-plugin-market](https://github.com/shengjiezhang1019-creator/lubi-plugin-market)。

作者手动申请 → 静态检查 → AI 报告 → 维护者审阅 → 批准或拒绝 → 机器人保存记录并反馈。

首次发布和版本更新均需作者手动申请，市场不会自动扫描作者仓库。
市场保存登记、审核记录和下载目录；源码保存在作者仓库。

| 要做什么 | 去哪里操作 |
| --- | --- |
| 查看审核报告，批准或拒绝插件 | 打开作者提交的那条 Issue，在评论区操作 |
| 检查审核为什么失败，或重新运行审核任务 | 打开市场仓库的 **Actions** 页面，选择 **Validate and review plugin**，进入对应运行记录 |
| 下架或恢复插件 | 打开市场仓库的 **Actions** 页面，选择 **Withdraw or restore plugin**，点击 **Run workflow** |
| 安全封禁或解除版本封禁 | 打开市场仓库的 **Actions** 页面，选择 **安全封禁或解除插件版本封禁**，点击 **Run workflow** |
| 启用或检查安全通知 | 打开市场仓库的 **Actions** 页面，选择 **启用安全通知**，点击 **Run workflow**；新市场首次授权见第 5.1 节 |

表中的英文名称是 GitHub Actions 页面里显示的工作流名称，用于定位对应操作。

## 2. 审阅检查结果与 AI 报告

系统检查申请、Release、版本历史、源码结构、清单、组件类型及依赖声明；通过后生成 AI 报告并评论到原申请。

市场只做静态审核，不运行插件或安装依赖。报告包含摘要、风险位置、证据、影响、建议和限制，原始 JSON 可展开查看。
维护者应结合报告证据和源码决定是否批准；普通提示不自动要求作者修改，静态检查通过也不代表功能已经实测。

允许随包提供包含安全默认值、空密钥或示例占位符的根目录 `config.toml`，不要求必须有 `config_schema`；根目录 `.env` 仍禁止发布。
TOML 格式检查不能判断是否包含真实凭据。结合 AI 报告和上下文核验疑似真实密钥、私人账号与私人配置，不因字段名称包含 `token`、`password` 就拒绝。审核意见不得复述敏感值。
默认 `config.toml` 可以随插件发布；市场检查 TOML 格式，真实凭据仍需结合报告人工核验。

批准前会复核报告、规则、源码提交和摘要，避免审核后内容变化。
批准复用已经展示的 AI 报告，不重新生成另一份建议。

## 3. 批准或拒绝申请

具有市场仓库 write/admin 权限的维护者，在开启中的申请下单独发送一条评论：

| 指令 | 作用 |
| --- | --- |
| `/approve` | 复核报告、规则、源码提交和摘要，发布市场目录后确认已上架 |
| `/reject` | 无需原因，保存拒绝记录，提示作者查看已有报告 |

点击绿色 **Comment**，不要点 **Close with comment**，由机器人反馈并关闭申请。
指令支持首尾空白、换行；编辑旧评论不会重新触发，需要发新评论。详细意见另发普通评论。
当前只支持以上两个评论指令。

确认批准成功时，应同时看到“已上架”标签和机器人确认评论。
申请关闭本身不能作为上架成功的依据；“已上架”表示批准记录和目录已成功推送。

## 4. 状态与异常处理

| 标签 | 含义与处理 |
| --- | --- |
| 检查中 | 正在处理；批准、拒绝时也会暂时出现，不代表重新调用 AI |
| 待人工审核 | 报告已生成，等待维护者审阅并决定 |
| 已上架 | 批准记录和目录已成功推送，申请随后关闭 |
| 不符合提交要求 | 查看机器人评论，确认规则违反或重复版本等原因 |
| 需修改后重新申请 | 已拒绝，申请随后关闭；作者修改源码后应升版本重新申请 |
| 审核暂未完成 | 查看 Actions 日志，处理网络、AI 或任务异常 |

AI 或网络暂时异常时，在 `Actions → Validate and review plugin` 重跑对应任务。
工作流代码已经修复时，重跑旧运行可能仍使用旧工作流，需要触发新的申请事件或指令。

报告因规则、提示词或下架状态变化而失效时，需要重新生成并审阅报告，按任务反馈重新申请。
同版本已批准或被拒绝后，不能通过另建 Issue 覆盖历史记录；新代码必须发布新版本。

## 5. 下架与恢复

进入市场 `Actions → Withdraw or restore plugin → Run workflow`，在默认分支填写插件名、操作和原因：

| 操作 | 作用 |
| --- | --- |
| `withdraw` | 下架整个插件，保留名称、原仓库绑定和版本历史 |
| `restore` | 恢复已有的已批准版本，适用于误下架等情况 |
| 修复版重新申请 | 原仓库发布高于全部历史记录的新版本，审核后用 `/approve` 同时恢复展示并发布新版 |

下架、恢复都要求维护者权限和原因。
下架不强制停用或卸载用户本地副本；目录缓存可能暂时显示旧信息。

确认恶意行为或密钥窃取等严重风险时，使用独立的“安全封禁或解除插件版本封禁”工作流。
安全封禁会停止问题版本的市场分发，并通知客户端停用，重启后移到隔离目录；不永久删除配置和数据。
市场工作流上线后，还需确认签名空名单已成功发布。客户端必须部署对应代码并配置可信公钥，才能执行封禁通知；单独发布市场不会重启用户服务。

### 5.1 首次配置安全通知

**当前市场已经启用，不用重新配置。** 平时封禁、解封插件，按下一节操作即可。

新市场第一次使用时，在电脑上打开市场项目文件夹，使用已登录的 GitHub 管理员账号运行：

```powershell
python -m market.security_setup
```

这条命令会自动完成以下事情：

- 生成给通知签名的私钥，并安全保存到 GitHub；私钥不会出现在终端或代码仓库里。
- 发布供露比核对通知来源的公钥，自动填写需要的 GitHub 设置。
- 发布“目前没有封禁任何插件”的第一份通知，并等待 GitHub 确认启用成功。
- 生成给程序安装包使用的公钥配置文件，保存为 `client_config/plugin_market_security_keys.json`。

不需要手工复制密钥、填写编号，也不需要另外发布第一份通知。
如果提示没有登录或权限不足，先用 GitHub 仓库管理员账号完成一次登录授权，再运行同一条命令。
命令默认使用当前 Git 仓库的地址；在其他目录运行时，可加 `--repository 你的用户名/市场仓库名` 指定市场。

以后想检查配置是否完整，在市场仓库打开 **Actions → 启用安全通知 → Run workflow**，选择默认分支后运行，无需填写其他内容。
重复运行不会换掉已有钥匙，也不会清空已经封禁的插件。若配置不匹配，程序会停止并说明原因，不会擅自覆盖。

新生成的私钥会在当前电脑用户目录的 `.lubi-plugin-market/keys/` 中保留受保护的备份。中途失败时重新运行，会尽量接着完成，不需要重新生成。
不要把私钥备份上传到代码仓库或发给用户；私钥泄露时应由管理员安排更换。

客户端公钥应随可信的程序安装包提供，不能让客户端自动信任网上下载的陌生钥匙。
本次会自动准备公钥配置文件；把它接入主程序安装包、部署客户端和重启服务，留到后续主程序发布时处理。

### 5.2 封禁与解除封禁

在默认分支打开 **Actions → 安全封禁或解除插件版本封禁 → Run workflow**：

| 字段 | 安全封禁 | 解除封禁 |
| --- | --- | --- |
| action | `ban` | `unban` |
| plugin_name | 已登记插件名 | 可留空 |
| version | 已批准版本，如 `1.2.0`，不带 `v` | 可留空 |
| record_id | 留空 | 原封禁记录编号，在上次工作流运行摘要中查看 |
| reason | 封禁原因，必填 | 解除原因，必填 |
| advice | 给用户的处理建议，如重启并更换 API Key | 可留空 |

工作流检查 write/admin 权限，将版本绑定到原仓库及完整提交，生成签名名单 `security.json`，与市场目录一起提交推送。推送失败不会报告成功，需查看运行日志。

封禁版本不再进入市场目录。有其他未封禁的已批准版本时，展示其中的最高版本；没有时隐藏安装入口。原批准记录保留，普通恢复上架也不能绕过安全封禁。

解除封禁只修改指定记录，并保留操作历史。同一版本仍有其他有效封禁时，继续禁止运行。客户端收到解除通知后，由用户选择恢复，不会自动运行；若原目录已有其他版本，恢复操作不会覆盖它。

作者发布修复版时，按正常流程重新申请、审核和上架。允许安装修复版，不需要解除旧问题版本的封禁。

### 5.3 发布前验证与处置边界

先在独立测试环境验证：通知签名、旧通知拒绝、断网后保留封禁、启用和重装不能绕过、重启隔离、隔离失败、解除后的恢复，以及修复版配置迁移。
自动测试使用临时密钥和插件目录，不发布真实封禁，也不处理真实用户插件。
正式启用前还应完成 GitHub 工作流与浏览器联调，检查页面顶部、插件卡片和日志中的提示。

客户端离线时收不到新通知。插件与主程序共用进程和文件权限，关闭钩子不能保证恶意代码停止，可靠停止仍需重启。
隔离仅移动插件目录，目录外的数据不会自动搬动；已经泄露的密钥仍需用户更换。本机制不构成安全沙箱。

用户需要配置的公钥、页面提示和恢复操作见[仓库部署说明](../README.md#插件安全通知)。

## 6. 客户端安装与更新验收

主程序下载已审核的固定提交 ZIP，校验摘要及结构，检查依赖，备份并加载插件。
下载包摘要不符时拒绝安装，不应跳过校验。作者后续提交不会改变已批准提交或用户本地副本。

新版本批准后，用户刷新市场并手动点击更新；发布 Release 或市场上架不会自动更新用户本机。
更新时应关注以下行为：

- 更新前备份旧插件和配置；Python 依赖按实际环境检查，必要时补装缺失库。
- 配置同路径同名保留用户值，新增字段用默认值，废弃字段移除，改名不猜测映射。
- 加载成功后记录新版；失败尝试恢复旧文件、配置和安装记录，页面说明恢复结果。
- 共享 Python 库不随插件回滚。

### 新闻插件更新验证示例

保持已安装 v0.1.2，不卸载；先把 `news.count` 改成 `2` 并保存，再更新到已批准的 v0.1.3，检查：

1. 更新前有版本提示，更新后版本显示 0.1.3。
2. count 仍为 2，新字段 `news.include_summary` 自动补为 true。
3. 关闭 include_summary 后，回复资料及来源详情不再包含 RSS 摘要。
4. 重启后版本、配置和功能正常。
5. 在独立测试环境模拟加载失败，验证旧插件及配置恢复。

截至原流程记录，发布、审核、人工决定、重复版本拦截和首次安装已有实际验证；v0.1.3 已有上架反馈。
客户端更新与失败恢复仍需按上述清单实测。主程序升级导致插件不兼容时，完整的强制升级和兼容版本选择机制尚未实现。

用户在露比“插件 → 市场”刷新目录、打开详情，点击安装或更新。
安装中显示步骤和进度；成功后收起步骤；失败显示原因、重试入口和可展开日志。
完成后留在当前页，用户应在已安装列表核对版本与加载状态，再实际调用功能。

## 7. 待维护事项与保留机制

原流程记录了以下可精简项，尚未修改对应代码：普通评论启动 gate 的开销、批准/拒绝显示“检查中”、重复遍历审核评论，以及辅助类继承分析产生的提示。

以下机制应保留：

- 旧标签映射用于历史兼容。
- 旧指令转义用于防注入。
- 目录 `comp_types` 用于自动分类。
- 批准前复核用于防止审核后内容变化。

市场仓库的 `docs/IMPLEMENTATION_STATUS.md` 含早期状态，需另行同步。
