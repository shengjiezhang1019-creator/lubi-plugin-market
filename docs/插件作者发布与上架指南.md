# 插件作者发布与上架指南

整理日期：2026-10-27。本文依据现有使用流程整理，流程状态截至 2026-10-26。

本文面向插件作者，说明从发布源码到申请上架、处理审核结果和发布更新的操作。
市场维护者的审核、批准及下架操作见[插件市场维护指南](PLUGIN_SECURITY.md)。

## 1. 流程与操作位置

准备插件文件 → 上传源码 → 发布正式 Release → 手动提交市场申请 → 查看审核结果。

| 操作位置 | 作者要做的事 |
| --- | --- |
| 自己的公开 GitHub 插件仓库 | 上传源码、发布正式 Release |
| [市场仓库](https://github.com/shengjiezhang1019-creator/lubi-plugin-market) | 提交申请、查看检查报告及维护者决定 |
| 露比网页“插件 → 市场” | 上架后验证安装及更新 |

源码保存在作者仓库；市场仓库保存登记、审核记录和下载目录。
首次发布和版本更新都需要手动申请，市场不会自动扫描作者仓库。

## 2. 准备插件文件

- 仓库根目录必须有 `_manifest.json`、`plugin.py`、`README.md`，以及插件所需源码和资源；不要多套一层目录。
- manifest 的 `name` 必须与申请插件名一致，`version` 必须与 Release 标签对应，例如 `0.1.3` 对应 `v0.1.3`。
- 第三方 Python 库在 `python_dependencies` 中声明包名和版本范围，不接受 URL、pip 参数或本地路径。
- 配置文件按内容区分：可以发布包含安全默认值、空密钥或示例占位符的根目录 `config.toml`；不应发布作者自己使用的真实密钥、私人账号及私人配置。根目录 `.env` 禁止随包发布。插件不一定有 `config_schema`，也可以通过 `config.toml` 提供默认配置。

本地市场代码已允许默认 `config.toml`，并检查 TOML 格式；疑似真实凭据由 AI 提示、维护者确认，报告不得复述敏感值。GitHub 线上规则尚未同步，发布这些修改后才会生效。

## 3. 上传源码并发布 Release

1. 在自己的插件仓库选择 `Add file → Upload files`，上传更改后的文件。
2. 填写说明，点击 `Commit changes`；分支受保护时通过 PR 合入。
3. 进入 `Releases → Draft a new release`，创建新标签，指向本次源码提交。
4. 填写发布说明，点击 `Publish release`，不保留草稿、不标记 Pre-release。
5. 核对标签下 manifest 的版本。保留旧标签，不移动标签或覆盖旧版本。

## 4. 提交市场申请

打开[添加插件或发布版本申请表](https://github.com/shengjiezhang1019-creator/lubi-plugin-market/issues/new?template=plugin.yml)。
以下以[新闻插件仓库](https://github.com/zhangshengjie-xsw/lubi-game-news)为例，实际填写时替换为自己的插件信息：

| 字段 | 示例 |
| --- | --- |
| 标题 | `[Plugin] game_news v0.1.3` |
| 插件名称 | `game_news` |
| GitHub 仓库 | `https://github.com/zhangshengjie-xsw/lubi-game-news` |
| Release 标签 | `v0.1.3` |
| 使用的 Hook | `BEFORE_REPLY_CONTEXT — 回复前补充参考资料` |
| 补充说明 | indienova 公开 RSS；依赖 aiohttp；新增 news.include_summary，默认 true；无需 API Key |

仓库填写根地址。Hook 至少选一项，以代码实际绑定为准，表单选择不会自动建立绑定。
示例版本已有申请，不要照抄后重复提交。

系统会检查申请、Release、版本历史、源码结构、清单、组件类型及依赖声明；通过后生成 AI 报告并评论到原申请。
市场只做静态审核，不运行插件或安装依赖。普通提示不自动要求修改，最终由维护者决定是否批准。

## 5. 查看审核结果

在市场的原申请查看标签和机器人评论。也可在 GitHub Issues 选择 `Created by me`，
或搜索 `is:issue author:你的用户名`。去掉 `state:open` / `is:open`，才能同时看到已关闭申请。

| 标签 | 含义 |
| --- | --- |
| 检查中 | 正在检查申请或生成审核报告 |
| 待人工审核 | 报告已生成，等待维护者决定 |
| 已上架 | 批准记录和目录已成功推送，申请随后关闭 |
| 不符合提交要求 | 违反规则或版本已有处理记录，查看评论原因 |
| 需修改后重新申请 | 维护者未批准，申请随后关闭 |
| 审核暂未完成 | 网络、AI 或任务异常，需要维护者处理 |

是否成功以“已上架”和机器人确认评论为准，不只看申请是否关闭。
站内及邮件通知取决于订阅与个人设置；个人主页没有专门的市场结果面板。

## 6. 处理问题与重新申请

| 遇到的问题 | 处理方式 |
| --- | --- |
| 申请字段填错 | 编辑尚未处理完成的申请正文，保存后重新检查 |
| 源码需要修改 | 修复、升版本、发布 Release，再创建新申请 |
| 同版本已批准或被拒绝 | 不能换 Issue 覆盖历史记录，新代码必须发布新版本 |
| AI、网络暂时异常 | 由维护者在 Actions 重跑对应任务，没有评论重试指令 |
| 报告因规则、提示词或下架状态变化失效 | 按任务反馈重新申请，由维护者重新生成并审阅报告 |

不要通过移动旧标签或覆盖旧 Release 来替换已审核源码。

## 7. 发布更新与处理下架

发布更新时，重复“修改源码、升版本、发布正式 Release、提交市场申请”的流程。
维护者批准后，用户刷新市场才会看到更新提示，再手动点击更新。
发布 Release 或市场上架都不会自动更新用户本机。

作者后续提交代码不会改变已批准的固定提交或用户本地副本。
建议在发布说明中写明功能变化、配置变化和新增依赖，便于审核及安装后验证。

插件被下架后，修复版应由原仓库发布高于全部历史记录的新版本，再提交审核。
维护者批准修复版后，可以同时恢复市场展示并发布新版。
下架不会强制停用或卸载用户本地副本。

上架后，在露比“插件 → 市场”刷新目录，打开插件详情并安装或更新。
完成后在已安装列表核对版本与加载状态，再实际调用功能。

### 更新后验证

建议在测试环境保留已安装的旧版本，修改一项配置并保存，再通过市场更新，检查：

1. 更新前能看到新版提示，更新后版本与发布版本一致，插件正常加载。
2. 同路径同名的配置保留用户值，新增配置使用新版默认值，已废弃配置按新版结构移除；改名字段需作者明确提供迁移或重新配置说明。
3. 新增功能及配置开关实际生效，原有主要功能仍可使用。
4. 重启后版本、配置和功能正常。

不要只验证卸载后重新安装；这种方式不能证明旧版本升级时能够保留用户配置。
