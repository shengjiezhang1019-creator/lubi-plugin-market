# 申请进度与结果反馈

反馈集中在市场仓库的申请 Issue，作者无需去个人主页查找。状态标签用于浏览列表，关键结果用新增评论反馈；GitHub 的邮件、站内通知取决于作者订阅与个人设置，不能保证标签变化会主动通知。

| 当前状态 | 含义与通知 |
| --- | --- |
| 检查中 | 已接受申请或授权重试，正在检查；只更新标签，不发送进度评论 |
| 不符合提交要求 | 明确违反申请或静态规则；评论说明必须修改项，源码修改后发布新版并重新申请 |
| 审核暂未完成 | AI 超时、服务或发布异常；评论说明重试方式，不据此要求作者修改插件 |
| 待人工审核 | 自动检查通过、完整 AI 报告已发布；报告评论明确尚未上架，等待维护者决定 |
| 已上架 | 维护者批准且索引成功推送；评论确认版本与 commit，再关闭申请 |
| 需修改后重新申请 | 维护者确认需要修改且记录成功推送；评论具体修改要求，再关闭申请 |

每次状态变化只替换以上流程标签，保留其他标签。标签缺失时由工作流创建，无需提前手工设置。

标签接口失败只记录维护提示，仍尝试发送结果评论和补完已发布申请。相同申请重复拒绝同一版本时，保留最初的拒绝原因与操作人，只补完标签、评论和关闭，不再次提交版本记录；其他申请或已批准记录不能被覆盖。

审核提示词也绑定规则指纹；复用 AI 报告和最终批准均核对当前提示词摘要。旧报告缺少摘要或提示词变化时，必须先 `/recheck`，再由维护者重新审阅。

已有批准或拒绝记录的版本，在申请入口直接提示处理结果及原申请编号，不重复下载源码或送交 AI。需要修改代码时应发布新版本；只有原申请的批准或拒绝命令可补完自身已发布结果，其他申请不能冒用此重试入口。

批准写入版本、登记和目录时，任一步失败都会尝试恢复写入前的精确内容。同一批准重试会核对目录是否与已批准记录一致；目录缺失、损坏或过期时重新生成并提交修复，不因“版本已批准”而跳过目录。如果存储持续故障导致回滚也失败，会明确要求维护者核对文件，不宣称发布成功。

批准和拒绝的重试都会重新检查索引文件的暂存内容：未提交则先提交，已提交则直接再次推送，推送成功后才记录发布完成并反馈结果。无法检查暂存区或推送失败时不宣布成功。

原申请已处理但尚未关闭时，编辑申请或 `/recheck` 会核对 GitHub 默认分支上的版本记录；只有状态、插件版本、仓库和原申请编号匹配，才恢复已上架或需修改后重新申请标签并补完关闭，不重新审核、不重复评论、不修改市场上下架状态。本地有记录但远程尚无记录时，不会被误判为已经发布。其他申请的重复版本仍按重复申请处理。

申请缺项、仓库地址或标签格式错误：编辑原申请修正，保存后重新检查。发布源码错误：修正并发布新版本，再更新原申请中的 Release 标签，不移动已发布版本的标签。市场 AI 或网络故障：通常无需修改插件，稍后评论 `/recheck`；作者或维护者可以重试。无权限的批准、拒绝、重试命令不更改申请状态，也不向作者发送误报。

批准前必须已发布完整检查与 AI 报告；批准不等于发布成功。git push 失败时不显示已上架、不关闭申请，提示维护者检查日志。若 push 已成功，后续评论或标签失败，失败反馈会保留已上架或需修改后重新申请状态并说明需要补完后续处理。

失败原因由受控中文模板生成，不直接发布异常正文、模型服务响应、源码或凭据。详细原始诊断仍在 Actions 日志中。每个运行 ID 和 attempt 的失败评论最多新增一次；新一轮重试仍会得到新结果通知。

工作流连申请检查阶段失败、缺少错误报告的运行环境故障也会尝试反馈；如果 GitHub 自身不可用或令牌无权发表评论，最终反馈仍可能无法送达，维护者需从失败的 Actions 查看原因。本文说明合并后的行为，不会给历史申请自动补发通知。

AI 报告统一显示“待人工审核”，保留所有风险证据及修改建议。普通静态提示不自动要求修改；AI 不能代替维护者决定拒绝或要求重新申请。`/reject 原因` 用于维护者确认修改要求，成功后显示“需修改后重新申请”。旧版本内部 rejected 记录保持兼容；旧标签会在该申请下一次处理时移除。
